# Архитектура HabitZen

HabitZen строится как одно мобильное приложение и один серверный контур Supabase на PostgreSQL. Внутри приложения функции разделены по смыслу: привычки, сегодняшний план, фокус, прогресс, дерево, профиль. Общими остаются оформление, локализация, диагностические события и платформенные возможности.

Этот этап фиксирует устройство проекта и создаёт проверяемые основы. Он не объявляет мобильное приложение или серверные команды готовыми.

## Почему PostgreSQL через Supabase

В личном задании показан Convex, а общий README разрешает Supabase. Supabase даёт PostgreSQL, аккаунты, API и защиту строк в одной согласованной системе. Миграции остаются SQL-файлами в Git. На телефоне нет пароля PostgreSQL и нет административного ключа.

Локально Supabase управляет Docker-контейнерами; отдельный самодельный Compose поверх его базы не нужен. Полный самостоятельный хостинг можно выбрать позже, когда будут известны сервер, домен и эксплуатационные требования.

## Границы приложения

```text
Expo Router / провайдеры
        ↓
Экран и компоненты конкретной функции
        ↓
Сценарий: создать привычку / отметить / изменить таймер
        ↓
Явный контракт операции
        ↓
Адаптер Supabase / локальное хранилище / возможности телефона
```

- `apps/mobile/src/app` — только маршруты. Запросы, расчёт серий и отрисовка сложных сцен сюда не складываются.
- `features/<функция>` — экраны и взаимодействие функции; слои application/data добавляются по мере появления реального кода.
- `packages/core` — правила дат, серий и таймера, независимые от React и сервера.
- `packages/design` — общие цвета, размеры и параметры движений.
- `packages/i18n` — выбор языка, перевод и форматирование дат/чисел.
- `packages/observability` — контракт логов и адаптер инструментов для Node.
- `supabase` — база, миграции, права и будущие транзакционные команды.

Пакеты экспортируют конкретные точки входа; одного общего файла, импортирующего всё приложение, нет. Сетевые данные впоследствии обслуживает TanStack Query; временное состояние интерфейса — локальные React hooks. Отдельное глобальное хранилище добавляется только для доказанной необходимости.

| Часть           | Ответственность                                                     |
| --------------- | ------------------------------------------------------------------- |
| onboarding/auth | Первый запуск, вход, подтверждение почты, восстановление, выход     |
| today           | План текущего дня, суммарный прогресс и навигация к привычке        |

Ни дерево, ни экран календаря не сохраняют независимую «правильную» копию прогресса. Основа — серверные планы и результаты, кеш является производным.

## Запись и повтор запроса

Команда получает идентификатор запроса и ожидаемую версию записи. Сервер определяет пользователя из проверенной сессии, сверяет право на запись, блокирует нужную строку и применяет изменение в одной транзакции. В `mutation_receipts` хранится результат и отпечаток содержимого команды.

Повтор того же requestId возвращает тот же результат. Повтор с другим содержимым отклоняется. Два одновременных изменения старой версии дают понятный конфликт, а не лишнее выполнение.

В начальной схеме запись привычек/планов/таймера клиенту закрыта. Это осознанная граница этапа: доступ откроют конкретные RPC в HZ-03, а не произвольная запись полей клиента.

## Даты и история

Момент события — `timestamptz`; календарный день — `date`; пояс — IANA-имя. Язык не определяет часовой пояс.

Расписание хранится версиями. План дня содержит снимок выбранного расписания и заголовка. После первого просмотра план фиксируется; добавленная сегодня привычка добавляется в сегодняшний план отдельной командой, без изменения прошлых дней. Для дней без входа план восстанавливается по версии расписания, действовавшей тогда. Массовое восстановление ограничивается страницами по диапазону дат.

Смена пояса действует для новых планов; уже существующий план той же даты повторно не создаётся. Дни, пропущенные из-за поездки через линию перемены дат, не дорисовываются как выполненные. Граничные случаи требуют отдельной интеграционной проверки в HZ-03.

Серия относится к запланированным дням. Незапланированный выходной нейтрален. Пропуск запланированного дня обрывает серию после окончания дня. Свайп «Сегодня отдых» не выдаёт выполнение и не начисляет прогресс; для уже запланированного дня он считается пропуском. Текущий незавершённый день не обрывает вчерашнюю серию раньше времени.

## Таймер

Таймер хранит срок завершения или остаток паузы; тики только перерисовывают экран. При возврате приложение сравнивает текущее время со сроком. Во время запуска использует монотонное время для отображения, после перезапуска — сохранённый срок; существенное изменение часов устройства требует сверки с сервером.

На аккаунт допускается одна активная или приостановленная сессия. Нажатие «завершить раньше» отличается от нормального завершения. Перерыв запускается отдельно. Локальное уведомление сообщает об окончании; бесконечный фоновый JavaScript не требуется.

## Расширение

Сначала — функции по заданию, надёжная синхронизация и хорошие экраны. Самостоятельный API, очередь фоновых задач, удалённые push и панель администратора появляются при конкретном требовании. Для тяжёлого серверного действия можно добавить Supabase Edge Function; чистые правила и контракты сохраняются.

Новые привычки, дополнительные награды и языки не должны требовать изменения навигации, механизма логов или ручных правок старых данных.

## Проверка качества

Строгий TypeScript, форматирование, линтер, тесты правил и ограничений БД выполняются в CI. Следующие этапы добавляют реальный Auth, проверки двух аккаунтов через API, Expo Doctor, сборку и сценарии на устройстве. Визуальное соответствие проверяется отдельно от правильности сохранения.
