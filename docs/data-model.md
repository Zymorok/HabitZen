# Данные и миграции

| Таблица           | Зачем нужна                                                   |
| ----------------- | ------------------------------------------------------------- |
| profiles          | Имя, IANA-пояс и предпочтение языка: system/ru/uk/en          |
| user_settings     | Тема, звук, вибрация, напоминания и уменьшение движения       |
| habits            | Постоянная личность привычки, название и оформление           |
| habit_schedules   | Версии расписания, выбранные дни, пояс и время напоминаний    |
| daily_plans       | Единственный план пользователя на календарную дату            |
| daily_plan_items  | Снимок привычки в плане, состояние, время выполнения и версия |
| focus_sessions    | Фокус/перерыв и восстанавливаемое состояние таймера           |
| mutation_receipts | Повторяемый результат одной команды по requestId              |

Владение данными проверяется составными внешними ключами и RLS. Нельзя присоединить расписание или отметку к привычке другого аккаунта. На одну привычку в одном плане допускается один результат; на аккаунт — одна активная сессия таймера.

Текущие правила доступа: пользователь читает только свои записи и меняет разрешённые поля профиля/настроек. Прямой клиентской записи привычек, планов и таймера нет.

Команды HZ-03 (миграция 20261018000100_habit_commands.sql): `create_habit`, `update_habit`, `archive_habit` и чтение `list_active_habits`. Каждая команда работает в одной транзакции, проверяет пользователя по сессии, версию строки и requestId. Повтор того же запроса возвращает сохранённый результат из mutation_receipts; тот же requestId с другим содержимым — конфликт. Ошибки приходят кодами PT401/PT404/PT409/PT422 (PostgREST превращает их в HTTP-статусы), приложение показывает вместо них понятный текст. Изменение расписания действует с сегодняшнего дня в поясе профиля, прошлые дни не переписываются. Архив не удаляет историю.

План дня (HZ-04, миграция 20261019000100_daily_plan_commands.sql): `open_today_plan` создаёт и фиксирует план на сегодня в поясе профиля по действующим расписаниям; позже в него добавляются только привычки, созданные сегодня. Для сегодняшнего дня показываются актуальные название и вид привычки, снимок в строке плана хранится для истории. `complete_plan_item`, `undo_plan_item`, `skip_plan_item` меняют только сегодняшнюю отметку (прошлые дни — PT409 day_closed), с requestId и версией. `day_outcomes` отдаёт итог каждого дня для серии: дни без открытого плана восстанавливаются по расписаниям того дня; «Сегодня отдых» по правилам проекта считается пропуском для серии, но не учитывается в прогрессе «N из M».

Фокус и прогресс (HZ-05, миграция 20261020000100_focus_and_progress.sql). Таймер хранит срок окончания (`deadline_at`), а на паузе — остаток (`remaining_ms`); время считает сервер. `current_focus` отдаёт активную сессию или что предложить дальше (перерыв — только сразу после полного занятия, в течение часа), число полных занятий и минут за сегодня и время сервера для поправки часов телефона. Идущая сессия со сроком в прошлом засчитывается как полная в момент срока, даже если приложение было закрыто. Команды `start_focus`, `pause_focus`, `resume_focus`, `finish_focus` («Завершить раньше» — неполное занятие), `reset_focus`, `skip_break` — с requestId и версией; одна активная сессия на аккаунт (PT409 focus_active). `calendar_days(from, to)` отдаёт по дням запланировано/выполнено/отдых для календаря; `day_outcomes` теперь строится на нём же, чтобы серия и календарь не расходились. `habit_days` — история одной привычки по дням: выполнено, отдых, пропуск, ждёт отметки, не запланировано. Выбранный звук хранится в `user_settings.focus_sound`.

Счётчики дерева и серии не принимаются от клиента. Прогресс дерева выводится из подтверждённых выполнений: одна отметка = один вклад; отмена убирает этот вклад. Начальный проектный порог уровня N — суммарно 5 × N × (N−1) выполнений, уровни 1–10. Формула — отдельное продуктовое решение HZ-06, которое будет закреплено тестами до реализации, а не случайное поле в UI.

## Правила миграций

1. SQL-файл с временем и понятным названием, явными ограничениями и правами.
2. Применение с нуля в отдельной базе и повтор запуска проверки всего набора.
3. Для изменения существующих данных — добавление новой структуры, перенос ограниченными порциями, проверка, затем удаление старого отдельным релизом.
4. После общего применения старые файлы не переписываются. Автоматический откат с удалением данных не используется.
5. Применение к удалённой базе — отдельная операция после резервной копии и проверки восстановления.

Полезно разделять: миграции сервера `supabase/migrations` и будущие миграции SQLite на телефоне. Их номера и жизненный цикл независимы.

Резервное копирование включает проверенный дамп данных и схемы, а при использовании Storage — сами объекты. История SQL-миграций не заменяет резервную копию.

Начальный SQL проверяется на PostgreSQL 17. Полный Supabase с настоящими JWT/Auth/Realtime и поведение RPC будут проверяться в HZ-03.
